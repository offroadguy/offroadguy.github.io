THE PROBLEM

Enterprise GenAI platform

Enterprise teams needed a shared platform for document Q&A, enterprise chat, incident intelligence and coding-agent workflows. These experiences depended on more than a model endpoint: documents had to be ingested, transformed and indexed; retrieval had to remain responsive; and model deployments needed repeatable artifact and runtime configuration. Different workloads also placed different demands on CPU, storage and GPU capacity.

What I owned

I owned GPU Kubernetes platform engineering, model-weight serving and onboarding tooling, Solr infrastructure and performance engineering, and Mac document-conversion infrastructure. I co-owned the wider enterprise AI platform with the team, including ingestion/inference GitOps onboarding and observability. Elasticsearch and Milvus were shared ownership.

  • Owned GPU Kubernetes platform build, lifecycle, tooling, capacity planning and production operations on AWS EKS, including upgrades, patching and incident response. Operated NVIDIA V100, A10G, L40S and A100 infrastructure.
  • Operated NVIDIA GPU Operator, Karpenter and cluster networking across environments, including Calico/Cilium. Connected GPU workload placement and cluster lifecycle decisions to model-serving requirements.
  • Designed and built model-weight serving and onboarding tooling: Helm/Argo CD, vLLM, S3-to-FSx staging, checksum validation and read-only mounts. Worked with tensor parallelism, GPU memory sizing, context limits and LoRA configuration.
  • Owned Solr infrastructure, performance, IaC and lifecycle tooling at approximately 200-node, multi-region scale. Supported 15,000+ embedding collections across five clusters in one region; co-owned Elasticsearch and Milvus.
  • Developed Go model-checksum and Kafka topic/user resource-generation tools. Built a TypeScript CLI to validate GPU allocation, tensor parallelism, model paths, storage mounts and startup probes before deployment.
  • Operated DCGM GPU monitoring with Prometheus/Grafana and co-owned wider observability. Led investigations across deployment readiness, storage/PVC failures, networking, queues and p95/p99 latency; coordinated root-cause analysis and corrective actions.
  • Coordinated US/APAC engineers, guided migrations and mentored teammates. Worked directly with customer leaders on incoming workloads, capacity and service constraints; partnered with developers on application GitOps onboarding.
  • Owned Mac conversion infrastructure, IaC and tooling; productionized EC2 Mac conversion with application developers.

SYSTEM DESIGN

Follow the architecture.

  1. 01

    Ingest enterprise knowledge

    Connectors and upload services stage source objects through an S3-backed access layer. Parsing, chunking and embedding services turn content into retrievable representations.

  2. 02

    Retrieve and orchestrate

    Search/vector services access Solr and OpenSearch indexes. Orchestration and agent services assemble context and invoke models through a routing layer. Kafka supports platform events and configuration dependencies.

  3. 03

    Serve models across two paths

    Self-hosted models run on a separate GPU EKS environment; a provider gateway reaches Vertex AI/Gemini. The model tooling stages weights to FSx for Lustre, validates checksums and mounts weights read-only for serving.

  4. 04

    Own the distributed foundation

    SolrCloud runs on EC2/EBS with ZooKeeper. Ansible-driven CloudFormation, Terraform foundations and Python utilities support provisioning, runtime configuration and lifecycle operations.

ENGINEERING JUDGMENT

The decisions behind the boxes.

Separate application and model infrastructure

The architecture separates the ingestion/inference services from GPU model hosting. This lets application and model deployments have distinct capacity and runtime configurations.

Make model artifacts part of deployment

Weight staging, integrity checks, shared volumes, health probes and runtime values are first-class deployment steps. Configuration covers precision, context limits, memory budgets, tensor parallelism and LoRA serving.

Treat retrieval as a systems problem

I worked across JVM/GC, OS settings, cache behavior, query patterns and indexes. The reported latency improvement is a vector-query result, not an LLM generation benchmark.

DELIVERY & OPERATIONS

What changed.

  • Supported 15,000+ project-embedding collections across five Solr clusters in one region, with at least 90% active; owned Solr infrastructure at approximately 200-node, multi-region scale.
  • Reduced vector-query latency from approximately 7.0 seconds to 1.9 seconds through JVM/GC, operating-system, cache, query and index tuning.
  • Migrated 200 Solr nodes to Graviton/ARM64 while preserving query throughput, reducing cost 19.8% ($266K+ annualized).
  • Production configurations specified 226 application-cluster workers across two AWS regions and 105 West-region document-processing replicas for parsing, chunking and PDF conversion. These are configured desired counts, not a live fleet inventory.
  • Delivered $500K+ in combined Solr and Mac infrastructure savings. Component rates: $266K+ annualized from Solr and approximately $16K/month from EC2 Mac document conversion. The combined figure is not stated as an annual total.

The operating story

I followed production failures across model artifacts, serving workloads, Kubernetes, storage and network dependencies. When incomplete model staging blocked checksum validation and serving readiness, I restored validated artifacts and made successful staging and validation a deployment prerequisite. I also diagnosed embedding-service timeouts caused by worker conntrack exhaustion, addressing connection pooling, bounded concurrency and conntrack sizing. DCGM GPU telemetry, Prometheus/Grafana, PCAP and application latency helped connect infrastructure behavior to user impact.
